\section{Introduction}
This chapter focuses on the overall presentation of our solution's architecture as well as that of the Apache Flink~\cite{FLINK} framework and Kubernetes~\cite{K8S}.
It highlights the key components of our system, how they interact and contribute to achieving our objective.

\section{Apache Flink framework overview}
Flink originates from the Stratosphere project, designed in 2008 by Professor Volker Markl and his team at the University of Berlin.
Flink has been one of the most important projects of the Apache Foundation since 2014.
In German, Flink means ``agile'' or ``fast'', like the squirrel in its logo.

Flink is an open-source framework for distributed processing of massive data.
It allows for efficient allocation and management of computing resources to run stream processing applications.
It integrates with all common cluster resource managers such as Hadoop YARN and Kubernetes, but can also be configured to operate as a standalone cluster or even as a library.
What makes it standout from others (such as Storm Hadoop MapReduce or Spark) is its native streaming API that offers extended functionalities.

\subsection{Technical architecture}
Flink operates and is deployed in a cluster of machines.
It works in a Master-Slave mode.
The master, called the JobManager, schedules tasks, distributes them to TaskManagers and tracks their execution progress.
It also allocates resources, and compiles results.
The slaves, called TaskManagers, execute the tasks sent by the JobManager and sometimes exchange data during different processing phases.
The core of the system lies in the processing engine (Runtime).
It can process data streams in streaming mode through the Stream Builder and the DataStream API as well datasets in batch mode with the batch optimizer and the DataSet API\@.
This execution engine is scalable and distributed, therefore enabling the processing of massive data (streaming or batch).
It also allows for the execution of iterative operations, memory management, and processing cost optimization.

\subsection{Components of a Flink cluster}

\subsubsection{JobManager}
The JobManager is the brain of our Flink cluster.
It has several responsibilities that enables the coordination of distributed execution of Flink applications: it decides when to schedule the next task (or set of tasks), reacts to completed tasks or execution failures and coordinates checkpoints and recovery in case of failure.
This process consists of three different components:

\begin{itemize}
    \item \textbf{ResourceManager:} It is responsible for the de-allocation and provisioning of resources in a Flink cluster.
    It manages task slots, which are the unit of resource scheduling in a Flink cluster.
    Flink implements several ResourceManagers for different environments and resource providers such as YARN, Kubernetes, and standalone deployments.
    In a standalone configuration, the ResourceManager can only distribute the slots of available TaskManagers and cannot start new ones by itself.
    \item \textbf{The Dispatcher:} The Dispatcher provides a REST interface to submit Flink applications for execution and starts a new JobMaster for each submitted job.
    It also runs the Flink WebUI to provide information about job executions.
    \item \textbf{The JobMaster:} The JobMaster is responsible for managing the execution of a single JobGraph.
    Multiple jobs can run simultaneously in a Flink cluster, each having its own JobMaster.
\end{itemize}

There is always at least one JobManager.
A high-availability configuration can have multiple JobManagers, one of them has to always be the leader, and the others are on standby.

\subsubsection{TaskManager}
TaskManagers (also called Workers) execute the tasks of a data stream, exchanging information through buffer memory.
TaskManagers are responsible for the effective execution of data processing operations.
They manage reading, writing and transformation operations within a Flink cluster.
There must always be at least one TaskManager.

The smallest unit of resource scheduling in a TaskManager is a task slot.
The number of task slots in a TaskManager indicates the number of simultaneous processing tasks.
One or more parallel instances of an operation can run in the same Task Slot.

Operations to be executed are divided into sub-tasks, depending on the default or specified parallelism options.
One or more parallel instances of an operation are carried out in a Task Slot.
The Task Slot represents an isolated memory space dedicated to the execution of one or more processing threads.
A TaskManager can have one or more Task Slots.

Each TaskManager sends a message called a \("\)heartbeat\("\) at regular time intervals and receives them from the JobManager to signal it is still functional.
If a TaskManager fails, the JobManager redistributes tasks among the operational TaskManagers by resuming the job from the last completed checkpoint.

\subsection{Job scheduling}
A Flink job is first in the \textit{created} state, then it is \textit{running}, and once its work is complete, it is \textit{finished}.
In case of failure, the job transitions to \textit{failing} and cancels all currently running tasks.
If all job vertices have reached the final state and the job cannot be restarted, the job has \textit{failed}.
If the job can be restarted, it will transition to the \textit{restarting} state.
Once the job has been restarted, it will reach the \textit{created} state.
If the user cancels the job, it will transition to the \textit{cancelling} state.
This also involves cancelling all currently running tasks.
Once all running tasks have reached the final state, the job transitions to the \textit{cancelled} state.
Unlike the \textit{finished}, \textit{cancelled}, and \textit{failed} states which denote a global terminal state and thus trigger job cleanup, the \textit{suspended} state is only locally terminal.
Locally terminal means that the job execution has ended on the respective JobManager, but another JobManager in the Flink cluster can retrieve the job from the persistent high-availability storage location and restart it.
Therefore, a job that reaches the \textit{suspended} state will not be completely cleaned up.

\subsection{Fault tolerance}

\subsubsection{Checkpointing}
One of Flink's strengths is its checkpointing mechanism.
This mechanism consists of taking automatic and asynchronous snapshots of the application state and position in the stream at regular intervals.
This provides the guarantee that each piece of data is processed at-least once with low performance impact.

In case of failure or breakdown, a Flink program with checkpoints enabled will resume processing from the last checkpoint.
The checkpoint mechanism can also be extended to writing and reading from a database.

Flink allows the user to manually trigger checkpoints; these are then called savepoints and allow, for example, stopping the program and resuming from the saved state, or restarting the application with different parallelism to adapt to changes in stream speed and volume.

\subsubsection{JobManager high availability}
The drawback of this type of architecture is the uniqueness of the master, which represents a single point of failure (SPOF), since by default, a Flink cluster contains a single JobManager.
If the JobManager fails, the TaskManagers notice but there is no procedure for electing a new JobManager among them because they are disconnected from it.
To mitigate this risk, Flink offers a procedure called High Availability.
The idea is to have a leader JobManager and one or more standby JobManagers, ready to take over if the leader fails or becomes unavailable.
Typically, this procedure is handled by a widely used underlying framework, ZooKeeper.
However, using high availability with ZooKeeper on Kubernetes incurs additional costs, as we must manage a ZooKeeper cluster.
On the other hand, Kubernetes provides a public API for leader election and configuration storage (e.g., ConfigMap).
We can leverage these features to make running a Flink cluster configured for high availability on Kubernetes more practical.

\subsection{Security}
When securing network connections between machine processes via authentication and encryption, Apache Flink distinguishes between internal and external connectivity.
Internal Connectivity refers to all connections established between Flink processes.
These connections run Flink's custom protocols.
Users never connect directly to internal connectivity endpoints.
External Connectivity refers to all connections established from outside to Flink processes.
This includes the Web UI and REST commands to start and control running Flink Jobs, including communication from the Flink CLI with the Job Manager/Dispatcher.
For greater flexibility, internal and external connectivity security can be enabled and configured separately.

\begin{center}
    \centering
    \includegraphics[width=0.9\textwidth]{img/flink_connectivity}
    \captionof{figure}{Connectivity}
\end{center}

\subsubsection{Internal connectivity}
Internal connectivity includes:
\begin{itemize}
    \item \textbf{Control messages:} RPC between Job Manager / Task Manager / Dispatcher / Resource Manager.
    \item \textbf{Data plane:} Connections between Task Managers for exchanging data during shuffling, broadcasting, redistribution, etc.
    \item \textbf{Blob service:} Distribution of libraries and other artifacts.
\end{itemize}

All internal connections are SSL-authenticated and encrypted.
Connections use mutual authentication, meaning that both the server and the client of each connection must present their certificate to each other.
The certificate effectively acts as a shared secret.

\subsubsection{External connectivity}
All external connectivity is exposed via an HTTP/REST endpoint, used for example by the Web interface and the CLI:
\begin{itemize}
    \item Communication with the Dispatcher to submit jobs (session cluster).
    \item Communication with the Job Manager to inspect and modify a running job/application.
\end{itemize}

REST endpoints can be configured to require SSL connections.
However, the server will accept connections from any client by default, meaning the REST endpoint does not authenticate the client.

\section{Kubernetes}
To deploy our solution, we will use Kubernetes~\cite{K8S} as a deployment platform.

\subsection{Overview}
Kubernetes, often abbreviated K8S, is an open-source container orchestration management system.
It automates the deployment, scaling, and management of containerized applications.
Designed by Google and now maintained by the Cloud Native Computing Foundation (CNCF), Kubernetes offers a robust solution for deploying, managing, and scaling containerized applications efficiently.
In addition, Kubernetes provides other key features including auto-scaling, load balancing, volume management, and secret management.
Furthermore, a web user interface facilitates cluster management and troubleshooting.
With these built-in features, Kubernetes often requires fewer third-party tools than Swarm or Mesos.

\subsection{Architecture}

\begin{center}
    \centering
    \includegraphics[width=1\textwidth]{img/k8s archi}
    \captionof{figure}{Kubernetes architecture}
\end{center}

Kubernetes has an architecture that offers a loosely coupled mechanism for cluster-wide service discovery.
A Kubernetes cluster has one or more control planes (Master Nodes), and one or more compute nodes (Worker Nodes).
Overall, the control plane is responsible for managing the entire cluster, exposing the Application Programming Interface (API), and scheduling the launch and shutdown of compute nodes based on a desired configuration.
Each compute node runs a container runtime like Docker with an agent, kubelet, that communicates with the control plane.
Each node can be a bare metal server or a virtual machine (VM), on-premise or in the Cloud.

\begin{itemize}
    \item \textbf{The Master Node:} is the control plane for a Kubernetes cluster. Its components are as follows:
    \begin{itemize}
        \item[-] \textbf{kube-apiserver:} As its name suggests, the API server exposes the Kubernetes API, which is the communication hub. External communications via the command-line interface (CLI) or other user interfaces (UI) pass through the kube-apiserver, as do all communications between control planes and nodes.
        \item[-] \textbf{Etcd:} The key-value store in which all cluster-related data is stored. Etcd is highly available and consistent, as all its accesses are made via the API server. The information contained in etcd is generally in user-readable YAML format (recursive acronym for ``YAML Ain't Markup Language'').
        \item[-] \textbf{kube-scheduler:} When a new pod is created, this component assigns it to a node for execution based on resource requirements, rules, and ``affinity'' specifications regarding geolocation and interference with other workloads.
        \item[-] \textbf{kube-controller-manager:} Although a Kubernetes cluster has several controller functions, they are all compiled into a single binary called kube-controller-manager.
    \end{itemize}

    \item \textbf{Worker Nodes:} These are the machines, namely virtual machines or physical servers, on which Kubernetes places pods to execute. Node components are as follows:
    \begin{itemize}
        \item[-] \textbf{kubelet:} Each node is associated with an agent called kubelet. It ensures that the container described in the PodSpecs specifications is running correctly.
        \item[-] \textbf{kube-proxy:} A network proxy on each node that manages network rules and enables communication between pods and network sessions, inside or outside the cluster, using the operating system's packet filtering where applicable.
        \item[-] \textbf{container runtime:} The software responsible for running containerized applications. Although Docker is the most popular, Kubernetes supports any runtime compatible with the Kubernetes CRI (Container Runtime Interface).
    \end{itemize}

    \item \textbf{Kubernetes Objects:}
    \begin{itemize}
        \item[-] \textbf{Pod:} The basic unit in Kubernetes, representing a set of one or more containers sharing the same network and storage space. Pods are deployed on nodes, and each node can run multiple pods.
        \item[-] \textbf{Service:} An abstract way to expose an application running on a set of Pods as a network service, thus enabling stable communication.
        \item[-] \textbf{Job:} An object that creates one or more pods and ensures they run to completion before terminating.
        \item[-] \textbf{Deployment:} An object that manages the creation, update, and scaling of applications in Kubernetes. It describes the desired state of the application and ensures that it is maintained, even in case of failure or update.
        \item[-] \textbf{ConfigMap:} An object that allows declaring configurations as key-value data. It is used to separate container configuration from pod specifications, thus facilitating configuration management. ConfigMaps can be mounted as volumes or used in environment variables to provide configurations to applications.
        \item[-] \textbf{Namespace:} A way to separate our Kubernetes cluster into multiple virtual environments identified by different names and that can be managed by different users.
    \end{itemize}
\end{itemize}

\subsection{Integration of Flink with Kubernetes}
Apache Flink can be deployed and integrated with Kubernetes to facilitate the management and deployment of Flink jobs on a Kubernetes cluster.
The integration of Flink with Kubernetes allows us to benefit from the following advantages:

\begin{itemize}
    \item[-] \textbf{Horizontal Scaling:} One of the key advantages of integration with Kubernetes is the ability to horizontally scale Flink jobs by adding or removing resources based on demand. Kubernetes facilitates this operation by automatically managing the container lifecycle.
    \item[-] \textbf{Resource Management:} Kubernetes manages the distribution of resources such as memory and CPU between different Flink pods, thus ensuring efficient utilization of cluster resources.
    \item[-] \textbf{Kubernetes Native Execution Mode:} Flink supports a native execution mode for Kubernetes, which allows deploying Flink clusters directly on Kubernetes clusters. The Kubernetes mode can be specified when configuring the Flink environment.
\end{itemize}


\section{Solution Architecture}
\label{sec:architecture}

This section describes the architecture of the LFU job from three
complementary viewpoints: the \emph{logical} architecture (functional
components and data flow), the \emph{deployment} architecture and the \emph{overall} architecture
(the end-to-end application in its ecosystem).

\subsection{Logical Architecture}
\label{sec:archi-logical}

The logical architecture organizes the system into functional layers,
independent of any deployment concern. Incoming Fair Use events flow
through a linear stream-processing pipeline that is enriched by an AI
inference stage before the notification is delivered.

\noindent Key points:
\begin{itemize}
    \item \textbf{Processing layer} — five Flink operators chained as a
    single dataflow (\texttt{Message Validation} $\rightarrow$
    \texttt{Check subscription eligibility} $\rightarrow$
    \texttt{AI anomaly prediction} $\rightarrow$
    \texttt{Notification Delivery} $\rightarrow$
    \texttt{Subscription Update}).
    \item \textbf{AI enrichment} — the ONNX model is embedded in the job
    artifact and queried in-process; it is non-blocking, with a
    rule-based fallback.
    \item \textbf{External services} — Valkey (subscription data) and
    Erable (notification) are all secured through authentication service.
\end{itemize}


\subsection{Deployment Architecture}
\label{sec:archi-physical}

The deployment architecture describes how the logical components are
deployed on the infrastructure. The job runs on a highly available
Apache Flink cluster orchestrated by Kubernetes, relying on
\emph{Kubernetes-native high availability} (leader election through
Kubernetes ConfigMaps and the API server) and persisting its state to
S3-compatible object storage.

\noindent Key points:
\begin{itemize}
    \item \textbf{High availability} — two JobManagers (active/standby)
    with leader election handled by Kubernetes (ConfigMap-based
    HA) with job state and HA metadata stored
    in S3.
    \item \textbf{Scalability} — three TaskManagers with two task slots

    \item \textbf{Observability} — each container exposes Prometheus

\subsection{Global architecture of the solution}

The overall architecture places the LFU job within its complete
ecosystem, from the upstream event producers to the end subscriber,
including all supporting services.

The figure above illustrates the detailed architecture of the Apache Flink cluster deployed on Kubernetes.
This configuration implements essential components to ensure reliability, high availability, and system monitoring.

Our job is deployed on a ``per-job'' Flink cluster, where each Flink job is deployed in a dedicated cluster that manages its own resources.
This deployment mode optimizes ease of maintenance and supervision.

\noindent Key points:
\begin{itemize}
    \item \textbf{End-to-end flow} — upstream systems publish Fair Use
    events to RabbitMQ; the LFU job consumes, validates, enriches
    with AI, and delivers notifications to subscribers via Erable.
    \item \textbf{Supporting services} — Valkey (state), S3
    (checkpoints/HA), OKAPI (authentication), Kubernetes-native HA
    (leader election), and Prometheus/Grafana (monitoring).
    \item \textbf{Embedded intelligence} — the ONNX model ships inside
    the job artifact, requiring no external model-serving
    infrastructure.
\end{itemize}

\subsection{Architecture components}

\begin{itemize}
    \item[-] \textbf{JobManager:} We have a single JobManager deployed as a Kubernetes pod managed by a Kubernetes ``Job'' object in our Flink cluster.
    \item[-] \textbf{TaskManager:} The TaskManager is deployed as a pod managed by a Kubernetes ``Deployment'' object.
    \item[-] \textbf{RabbitMQ:} RabbitMQ~\cite{RBMQ} is an open-source messaging software designed to manage communication between distributed applications. It uses the AMQP standard to transfer messages between applications. Its communication model is based on the concept of a queue, which is a container storing messages sent by producers. These messages are then retrieved by consumers and transferred through exchanges that route messages to queues. Our job consumes messages from RabbitMQ using the AMQPS protocol, which guarantees both security and performance of exchanges.
    \item[-] \textbf{External APIs:} Our Flink job must consume information from two external APIs: the Valkey API (for subscription retrieval and updates) and the Erable API (for notification dispatching). To do this, specific network flows must be opened from our cluster to the host machines of these APIs. In addition, all requests pass through the API Gateway to ensure the authenticity and traceability of calls. This architecture guarantees not only the security of exchanges with external APIs, but also centralized and secure management of authentication and call monitoring.
    \item[-] \textbf{ONNX Runtime:} ONNX Runtime is a high-performance inference engine for deploying machine learning models in the ONNX (Open Neural Network Exchange) format.
    It enables our Flink job to execute ML model inference directly within the data processing pipeline, ensuring low-latency predictions without the need for external model serving infrastructure. ONNX Runtime supports hardware acceleration and is optimized for both CPU and GPU execution, providing efficient and scalable inference capabilities integrated into our streaming application.
\end{itemize}

\subsection{State management}
Our Flink job is designed to periodically save its state in an S3~\cite{s3} bucket using the checkpointing mechanism.
This approach ensures reliable recovery in case of failure, as we can retrieve the previous state from S3~\cite{s3}.
Additionally, we have implemented the ``at-least-once'' guarantee, meaning that each message is processed at least once.
This guarantee reinforces the reliability of our system, ensuring that data is correctly processed even in the presence of potential disruptions.

\subsection{Scalability management}
Our cluster adapts efficiently to increased load.
It is capable of creating TaskManagers on the fly and removing them based on the amount of data to process.
This flexibility provides optimal resource management, guaranteeing efficient adaptation to workload variations.

\subsection{Single point of failure management}
Since the JobManager represents our Single Point of Failure (SPOF), we have implemented the high availability management mechanism offered by Kubernetes, namely leaderElection, implemented by Flink.
This ensures the redeployment of the JobManager and the recovery of its last state from S3~\cite{s3} upon each failure, guaranteeing continuity of data processing even in case of disruption.

\subsection{Log management}
We have integrated a syslog container as a sidecar with each application container, thus enabling log reception.
These logs are then redirected to our log processing system, where they are analyzed and visualized in the Kibana dashboard.

\subsection{Metrics management}
A monitoring component is deployed in a separate Kubernetes namespace from the one where our Flink job is deployed.
The Prometheus server collects metrics at regular intervals in order to provide them to Grafana for exploitation.
