\section{Project Structure}

The \texttt{LEVEE FAIR USE} project exists within a bundle of other topologies called \texttt{PushaVoo Flink} which is organized into Maven modules:

\begin{itemize}
    \item \texttt{pushavoo-flink-core} --- Shared module (utilities, metrics, RabbitMQ connectors, Erable client, Valkey access)
    \item \texttt{pushavoo-flink-jobs/*} --- The module that conatins all the jobs of the PushaVoo Flink project
    \item \texttt{pushavoo-flink-jobs/job-fair-use} --- The LFU job (subject of this report)
    \item \texttt{pushavoo-flink-test} --- Shared test module
\end{itemize}

The shared aspect of our project structure allows for the reuse of common components, utilities, and configurations across different jobs within the PushaVoo Flink project.
This modular approach promotes maintainability, scalability, and consistency in development practices.

\section{Job Workflow}

Figure~\ref{fig:job-workflow} details the different steps a message goes through before being transmitted to the Erable API for notification dispatching. Our Flink job continuously consumes messages from RabbitMQ, connecting to a queue where events arrive in a continuous stream. It then proceeds to JSON conversion and deserialization into the internal data model.

The next step consists of validating the message format according to predefined constraints (valid French MSISDN, non-null fields, valid event type). If the message is non-compliant, it is rejected, and processing moves on to the next message.

After that, we retrieve the subscription from the Valkey API by making a request with the customer's identifier (MSISDN). We then enrich the message with information such as the historical notification state and the last notification timestamp per event type. Next, we verify whether the customer is eligible for notification by applying the business rules that determine notification eligibility based on customer type, threshold levels, and historical state.

Before sending the message to the Erable API, which is responsible for directly notifying the customer, we pass it through the AI prediction module that evaluates the quota overshoot probability. Finally, we update the notification date in the customer's subscription by calling the Valkey API.

\section{RabbitMQ Source Operator}

RabbitMQ~\cite{RBMQ} plays a central role as the primary data source for our Flink job. The source consumes JSON messages from the queue configured via the \texttt{RMQ\_LFU\_QUEUE} environment variable. It uses a custom RabbitMQ connector (\texttt{CustomRmqSource}) that optionally supports \textit{correlation ID} for message tracking.

It is important to note that the connection to RabbitMQ is made via the secure AMQPS protocol, guaranteeing a secure connection and reinforcing the reliability and confidentiality of data exchanges.

\begin{lstlisting}[language=Java, caption={RabbitMQ source creation}, breaklines=true]
CustomRmqSource<String> source =
    RmqUtils.createCustomRmqSource(
        RMQ_LFU_QUEUE, USE_CORRELATION_ID);
DataStream<String> stream = env.addSource(source)
    .name("RabbitMQ").uid("rabbit-mq").rebalance();
\end{lstlisting}

Figure~\ref{fig:rabbit-queue} shows the RabbitMQ management UI view of our source queue. It displays the queue's real-time statistics including the message rate, the number of ready and unacknowledged messages, and the consumer connection status. This interface allows us to monitor the ingestion throughput and verify that our Flink source operator is actively consuming messages from the configured queue.
